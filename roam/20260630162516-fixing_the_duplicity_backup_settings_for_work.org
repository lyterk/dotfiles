*** S3 Credentials: Recommendation

*Use =sops-nix=* over password-store for this use case. Reasons:
- Secrets are decrypted at boot to =/run/secrets/= — duplicity can read them as a file
- Works well with NixOS system services (which run as root, not your user)
- =pass= is user-session oriented and awkward to wire into systemd services

The =secretFile= for duplicity should export:
#+begin_src bash
AWS_ACCESS_KEY_ID=AKIAxxxxxxxx
AWS_SECRET_ACCESS_KEY=xxxxxxxx
#+end_src

*sops-nix setup sketch:*
#+begin_src nix
# In your configuration.nix
sops.secrets."duplicity-aws" = {
  sopsFile = ./secrets/duplicity-aws.yaml;
  mode = "0400";
};
#+end_src

#+begin_src yaml
# secrets/duplicity-aws.yaml (encrypted with sops)
duplicity-aws: |
  AWS_ACCESS_KEY_ID=AKIAxxxxxxxx
  AWS_SECRET_ACCESS_KEY=xxxxxxxx
#+end_src

The IAM user should have a minimal policy — only =s3:GetObject=, =s3:PutObject=, =s3:ListBucket=, =s3:DeleteObject= on your specific bucket.

You can export the function via =lib.mkOption= or simply by returning it as part of the module's =config= and using a custom option. The simplest approach is to add it to a shared =lib= overlay, but the idiomatic NixOS way is to use module options.

*shared/duplicity.nix* — export only the function:

#+begin_src nix
{
  config,
  lib,
  pkgs,
  ...
}:
let
  mkDuplicityConfig =
    {
      homedir,
      targetUrl,
      secretFile ? null,
    }:
    {
      # ... same as before
    };
in
{
  # Export the function so other modules can use it
  options.lib.mkDuplicityConfig = lib.mkOption {
    type = lib.types.raw;
    default = mkDuplicityConfig;
    readOnly = true;
  };
}
#+end_src

*Then in another file* (e.g., =hosts/myhost/default.nix=):

#+begin_src nix
{ config, lib, ... }:
{
  imports = [ ../../shared/duplicity.nix ];

  services.duplicity = config.lib.mkDuplicityConfig {
    homedir = "/home/lyterk";
    targetUrl = "s3://s3.amazonaws.com/your-bucket-name/lyterk";
    secretFile = "/run/secrets/duplicity-aws";
  };
}
#+end_src

The key is =lib.types.raw= which allows passing arbitrary values (including functions) through the option system, and =readOnly = true= to prevent overriding.

** Having more than one service

For a per-user setup with NixOS (not home-manager modules), the cleanest approach is to configure =services.duplicity= instances per user in each host's configuration file, using the shared helper.

Since =services.duplicity= is a NixOS service (not home-manager), it runs as root but can back up user directories. You'd configure it per-host with the specific user's home:

#+begin_src nix
# hosts/myhost/configuration.nix
{ config, lib, ... }:
{
  imports = [ ../../shared/duplicity.nix ];

  services.duplicity = config.lib.mkDuplicityConfig {
    homedir = "/home/lyterk";
    targetUrl = "s3://s3.amazonaws.com/your-bucket/hosts/myhost/lyterk";
    secretFile = "/run/secrets/duplicity-aws";
  };
}
#+end_src

*If you have multiple users on one host*, =services.duplicity= only supports one instance. You have two options:

1. *Extend =mkDuplicityConfig=* to merge multiple users' includes into one backup job (simpler, one S3 path per host).

2. *Use systemd services directly* — create a =systemd.services.duplicity-<user>= for each user, giving you true per-user isolation:

#+begin_src nix
# shared/duplicity.nix — add alongside mkDuplicityConfig
mkDuplicitySystemdService = { user, homedir, targetUrl, secretFile }: {
  description = "Duplicity backup for ${user}";
  startAt = "daily";
  serviceConfig = {
    User = "root";
    ExecStart = /* duplicity command */;
    EnvironmentFile = secretFile;
  };
};
#+end_src

Then in your host config:
#+begin_src nix
systemd.services.duplicity-lyterk = mkDuplicitySystemdService { ... };
systemd.services.duplicity-otheruser = mkDuplicitySystemdService { ... };
#+end_src

To encrypt Duplicity backups with your GPG key, you need to pass =--encrypt-key= to Duplicity. Here's how to modify your setup:

** 1. Add your GPG key ID to sops secrets

In your =secrets.yaml=, add your GPG key ID (or fingerprint):
#+begin_src yaml
gpgKeyId: "YOUR_KEY_FINGERPRINT"
#+end_src

Or more practically, since Duplicity needs the key ID at runtime, you can hardcode the key ID (it's not secret) and just ensure the key is imported.

** 2. Modify =duplicity.nix= to accept and use a GPG key ID

#+begin_src nix
mkDuplicityService =

    user,
    homedir,
    targetUrl,
    secretFile ? null,
    gpgKeyId ? null,  # Add this parameter
  }:
  {
    description = "Duplicity backup for ${user}";
    startAt = "daily";
    serviceConfig = {
      User = "root";
      ExecStart = lib.concatStringsSep " " (
        [ "${pkgs.duplicity}/bin/duplicity" ]
        ++ (lib.optionals (gpgKeyId != null) [ "--encrypt-key" gpgKeyId ])
        ++ [ "--volsize" "100" ]
        ++ [ "--full-if-older-than" "1M" ]
        ++ (mkExcludeFlags homedir)
        ++ [ homedir targetUrl ]
      );
      EnvironmentFile = lib.mkIf (secretFile != null) secretFile;
    };

#+end_src

The error says =the key 'duplicityAws' cannot be found= in your =duplicityAws.json= file. The key in the JSON must match the secret name.

Your =duplicityAws.json= needs to look like:

#+begin_src json
{
    "duplicityAws": "AWS_ACCESS_KEY_ID=AKIAxxxxxxxx\nAWS_SECRET_ACCESS_KEY=xxxxxxxx",
    "sops": { ... }
}
#+end_src

To create it properly:

#+begin_src bash
# Create the plaintext file first
cat > /tmp/duplicityAws.json << 'EOF'
{
    "duplicityAws": "AWS_ACCESS_KEY_ID=AKIAxxxxxxxx\nAWS_SECRET_ACCESS_KEY=xxxxxxxx"
}
EOF

# Encrypt with sops
sops --encrypt /tmp/duplicityAws.json > /etc/nixos/secrets/duplicityAws.json
#+end_src

The key inside the JSON file must exactly match the secret name used in your sops config (=duplicityAws=).
