* Encryption
#+BEGIN_QUOTE
Right now, these backups aren't encrypted. I already have a gpg key on the host, how can I direct duplicity to use that (or an age key, or ssh, whatever is simplest)
#+END_QUOTE


Duplicity has native GPG support, so using your existing GPG key is the simplest path. You just need to pass =--encrypt-key <KEYID>= (and optionally =--sign-key <KEYID>=) and set =PASSPHRASE= in the environment (needed even for public-key encryption, though it can be empty if your key has no passphrase; for signing you'll need the real one).

Here's how to modify your =duplicity.nix=:

#+begin_src nix
mkDuplicityService =
  {
    user,
    homedir,
    targetUrl,
    secretFile ? null,
    encryptKey ? null,
    signKey ? null,
  }:
  {
    description = "Duplicity backup for ${user}";
    startAt = "daily";
    serviceConfig = {
      User = "root";
      ExecStart = lib.concatStringsSep " " (
        [ "${pkgs.duplicity}/bin/duplicity" ]
        ++ lib.optionals (encryptKey != null) [ "--encrypt-key" encryptKey ]
        ++ lib.optionals (signKey != null) [ "--sign-key" signKey ]
        ++ [ "--volsize" "100" ]
        ++ [ "--full-if-older-than" "1M" ]
        ++ (mkExcludeFlags homedir)
        ++ [ homedir targetUrl ]
      );
      EnvironmentFile = lib.mkIf (secretFile != null) secretFile;
    };
  };
#+end_src

Then in your host config, when you call =mkDuplicityUser=, pass =encryptKey = "0F39E83B";= (your existing key ID).

The =secretFile= should contain at minimum:

#+begin_src 
PASSPHRASE=your-gpg-passphrase
#+end_src

If you're only encrypting (not signing) and want to avoid the passphrase entirely, add =--no-encryption= is wrong — instead you can use a key with no passphrase, or set =PASSPHRASE== (empty) and duplicity will only need it for restore.

A few gotchas since this runs as root:

1. *GPG home*: root won't see your user's keyring. Either import the public key into root's keyring (=gpg --import= as root), or set =GNUPGHOME=/home/lyterk/.gnupg= in the =EnvironmentFile=. For encryption you only need the public key, so importing to root's keyring is cleaner:
   #+begin_src 
   sudo gpg --import /home/lyterk/pubkey.asc
   sudo gpg --edit-key 0F39E83B trust  # set ultimate trust
   #+end_src

2. *Cleanup command* also needs the same =--encrypt-key= flag (or it'll complain), so pass it through there too.

3. Consider running the service as your user instead of root if the homedir is readable — simpler GPG story. But then you lose access to files owned by other users.

Alternative: if you want to avoid GPG passphrase juggling, use *symmetric encryption* with just =PASSPHRASE=<long-random-string>= in the secret file and no =--encrypt-key=. Duplicity encrypts with that passphrase via GPG symmetric cipher. Simplest possible setup, and you already have sops for storing the passphrase.

* Per-user, and causality
** When to start the timer
#+BEGIN_QUOTE
This machine is a laptop, which very likely will be closed (+ suspended) at midnight. How will systemd handle that? How should I?
#+END_QUOTE

*** How systemd handles missed timers

With =startAt = "daily"=, NixOS creates a =systemd.timer= with =OnCalendar=daily= (midnight). By default:

- *If suspended at trigger time*: the timer does /not/ fire during suspend, and it does /not/ automatically catch up when you resume — unless =Persistent=true= is set.
- *If the machine is off*: same thing — missed without =Persistent=true=.

*** What you should do

Set =Persistent = true= on the timer. Then systemd stores the last run time on disk and, on resume/boot, if the scheduled time was missed, it runs the unit immediately.

Since =startAt= only gives you the calendar spec, use =timerConfig= to add persistence. Something like:

#+begin_src nix
{
  description = "Duplicity backup for ${user}";
  startAt = "daily";
  timerConfig = {
    Persistent = true;
    RandomizedDelaySec = "30min";  # optional: avoid thundering herd on resume
  };
  serviceConfig = { ... };
}
#+end_src

Note: =startAt= + =timerConfig= both work — NixOS merges them (=startAt= sets =OnCalendar=, =timerConfig= fills the rest).

*** Extra considerations

1. *Network/target availability on resume*: if =targetUrl= is remote (S3, SSH, etc.), duplicity may run before the network is up. Add to the /service/:
   #+begin_src nix
   after = [ "network-online.target" ];
   wants = [ "network-online.target" ];
   #+end_src

2. *Battery*: you probably don't want a 100-volsize backup to kick off the moment you open the lid on battery. Options:
   - =ConditionACPower=true= in =unitConfig= (skips if on battery — but then it's skipped, not deferred).
   - Or a small script wrapper that waits for AC.

3. *Randomized delay* helps if you resume and /both/ the backup and cleanup fire immediately alongside other daily jobs.

4. *=OnCalendar=daily= = midnight exactly.* Consider ="*-*-* 12:00:00"= (lunchtime) or similar if you're more reliably awake then — reduces reliance on =Persistent=.

Minimal fix: just add =timerConfig.Persistent = true;= to both services.

    user,
    homedir,
    targetUrl,
    secretFile,
    ...
  }:
  {
    description = "Duplicity backup for ${user}";
    after = [ "network-online.target" ];
    wants = [ "network-online.target" ];

    unitConfig = {
      ConditionACPower = true;
    };

      Persistent = true;
      RandomizedDelaySec = "3hr";

    serviceConfig = {
      User = user;
      Group = user;

      RuntimeDirectory = "duplicity-${user}";
      ExecStart = lib.escapeShellArgs (
        [
          "${pkgs.util-linux}/bin/flock"
          "--nonblock"
          "/run/duplicity-${user}/lock"

      EnvironmentFile = secretFile;

Key changes:

1. *=User = user; Group = user;=* — runs as the target user instead of root.
2. *=RuntimeDirectory = "duplicity-${user}"=* — systemd creates =/run/duplicity-${user}/= owned by that user, cleaned up automatically.
3. *=flock=* wraps duplicity:
   - Backup uses =--nonblock=: if a backup is already running (e.g. previous still going), it exits immediately instead of stacking up.
   - Cleanup blocks (waits) for the lock since it =requires= the backup service anyway; this guarantees they don't overlap.
4. Both services share the same lock file, so backup and cleanup are mutually exclusive.

*Caveats to verify:*
- =secretFile= must be readable by =user= (or use =LoadCredential== for stricter handling).
- The user needs write access to any local target path (irrelevant if =targetUrl= is remote like S3/B2).
- =~/.cache/duplicity= (signature cache) will now live in the user's home — make sure it's not in your exclude list (it isn't, good).
